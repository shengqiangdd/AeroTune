# Windows update design

## Current state

- The production NSIS installer is `perMachine` and installs AeroTune under protected `Program Files` (`src-tauri/tauri.conf.json`). That boundary matters: AeroTune can explicitly relaunch itself elevated, and the optional `AeroTune-ElevatedTest` task is deliberately restricted to the protected executable.
- The Cargo build guard pins root `productName`, `identifier`, and `version` to AeroTune's protected identity and Cargo package version, rejects serde aliases, forbids `mainBinaryName` overrides, and requires both base config and overlays to leave `bundle.windows.signCommand` and `bundle.windows.nsis.installDir` unset. Tauri derives the Windows install folder and installer names from `productName`; the fixed task expects the AeroTune executable.
- Tauri's `beforeBuildCommand` uses `scripts/build-frontend-sanitized.mjs`, which removes all updater signing credential variables before spawning `npm run build`. The signed release command separates `tauri build --no-bundle` (credentials stripped before Cargo/build scripts) from `tauri bundle` (the signing stage); contract tests receive neither signing material nor inherited updater overlay/runtime configuration. Only the release orchestrator, guarded preflight/wrapper, and final bundler receive signing material. The bundle wrapper maps a path-only `TAURI_SIGNING_PRIVATE_KEY_PATH` input to Tauri's `TAURI_SIGNING_PRIVATE_KEY` build/bundle input and removes the signer-only alias before launching the bundler. The orchestrator snapshots the validated JSON overlay and uses that same temporary file for required preflight and bundling, then removes it. Base `beforeBundleCommand` stays unset, and the release overlay is nested-key allowlisted as well: it cannot inject a Windows `signCommand`, NSIS `installDir`/hooks/template, custom updater headers, or override `build`/`app` configuration.
- A Rust Tauri updater integration is present, but the default build has no embedded feed/public key, no signed artifacts, and no release publication workflow. The update plugin has no frontend permission, and the update command remains disabled unless a protected task and audited pipeline are ready. The current installer is not Authenticode-signed.
- Therefore the current release is a manually launched installer. A non-elevated app cannot silently rewrite a per-machine install.

## Why a normal updater is not enough

Tauri's updater requires signed artifacts. A release must keep its Minisign private key outside the repository/installer (for example, a protected CI secret), embed only a structurally valid Tauri Minisign public key (release preflight and Rust runtime both parse the base64-wrapped key), publish the matching signature and version metadata over HTTPS, and require signed-version binding. A missing key/feed must leave updates disabled. The updater dependency is pinned to 2.14.0 with AeroTune's local bounded-manifest patch; upgrades require manually rebasing and reviewing that patch; `requireSignedVersion: true` is mandatory because the feed manifest itself is not signed and version metadata must be bound to the signed artifact; `dangerousInsecureTransportProtocol`, `dangerousAcceptInvalidCerts`, and `dangerousAcceptInvalidHostnames` are explicitly false and rejected when true in build/release overlays. Guards also reject Tauri's hyphenated serde aliases (such as `require-signed-version` and `allow-downgrades`) so alternate spellings cannot bypass these checks ([Tauri updater security advisory](https://github.com/advisories/GHSA-p8c6-29q6-cqw7)). The frontend has no updater plugin permission; update requests go through the restricted Rust commands and fixed task.

Tauri's Windows updater UI mode is separate from OS permissions. `passive` can show progress, but does not grant admin rights. `quiet` cannot request admin; it only works for a user-wide install or when the app already runs elevated. With AeroTune's protected per-machine install, calling the updater from the ordinary UI would still require UAC on each update. Do not set `quiet` and claim it removes elevation. Base and helper configs pin `windows.installMode` to `quiet` only for an already-elevated fixed runner and set `windows.installerArgs` to an empty array; build/release guards reject overrides because arbitrary NSIS/MSI arguments could redirect installation outside protected Program Files. The code-level updater guard also blocks Tauri's built-in `Update::install` path, which stages through user temp rather than the audited protected runner.

## Chosen direction

Keep the per-machine installation and its protected executable path. The intended no-repeat-UAC design is a dedicated `--aerotune-update-only` execution path under a separately provisioned fixed task. The current scaffold reuses `AeroTune.exe` but starts a helper context with no windows or app command handler; it is not yet a standalone updater binary. The task action must be fixed (no user-supplied command or path), user access must be run-only, and it must independently validate the HTTPS source, Tauri signature and signed version, target architecture, strict SemVer precedence progression (build metadata alone does not count), staged-file path/ACL/reparse points, and rollback artifact before installing. Keep it separate from `AeroTune-ElevatedTest`; that task launches the full app and must not become a general updater.

The ordinary AeroTune UI may request only the fixed updater task. Update-only mode checks bounded feed-response, pipeline, DNS, system-proxy, bounded-download, and task-attestation readiness before constructing the updater plugin, so current hard-off gates stop even feed requests. The normal UI deliberately does not register Tauri's built-in updater plugin, and its check command refuses to instantiate it; release preflight rejects overlays that override app capabilities and recursively scans capability files for updater plugin permissions. The Cargo build script independently checks local Tauri configs plus the effective `TAURI_CONFIG` overlay, rejects updater permissions/artifacts while hard-off gates remain set, and blocks unsafe direct CLI builds that invoke Cargo. The checked-in `npm run tauri` wrapper forbids custom runners; a raw CLI invocation with its own custom runner can still skip Cargo checks, so never publish outputs from raw CLI builds. The privileged runner must never execute arbitrary scripts or user-selected files. The Rust update-only path and fixed-task registration script are present, but rollback and privileged Windows validation are not complete. The helper derives Program Files through `SHGetKnownFolderPath` instead of trusting a process `ProgramFiles` environment override, then checks the executable/install path for reparse points; this is not runtime ACL attestation. The feed-response cap (`UPDATE_FEED_RESPONSE_BOUNDED_READY`), runtime pipeline (`UPDATE_PIPELINE_READY`), DNS destination (`UPDATE_DNS_DESTINATION_POLICY_READY`), system proxy policy (`UPDATE_PROXY_POLICY_READY`), bounded download/staging (`UPDATE_BOUNDED_DOWNLOAD_READY`), task-definition attestation, and task-registration switches are hard-coded off; do not register the task yet. Until rollback, signature/version checks, and task DACL pass review on a disposable Windows setup, updates remain disabled. A standard Tauri updater alone is not an acceptable substitute for this per-machine no-prompt requirement.

Upstream `tauri-plugin-updater` 2.14.0 `Updater::check` calls `Response::json().await` directly without an explicit response-body size cap. AeroTune now vendors a local patch that replaces this with bounded streaming JSON accumulation (256 KiB prototype cap), early `Content-Length` rejection, actual-byte counting, and short/truncated-body rejection. The patch has unit coverage for over-limit, unknown-length, truncation, exact-cap, and invalid-JSON cases. `UPDATE_FEED_RESPONSE_BOUNDED_READY` remains false until the vendored change and cap are reviewed and measured against real feed metadata. Patch provenance and upgrade/rebase notes are in [UPSTREAM_PATCH.md](vendor/tauri-plugin-updater/UPSTREAM_PATCH.md).

Critical blockers found in review: Tauri's Windows updater stages the verified NSIS payload in a temporary directory and launches that file, so the elevated task must not use `download_and_install` until protected staging and a post-copy integrity check eliminate same-user temp replacement risk. The Rust readiness path embeds the provisioning script's read-only `Verify` action, which checks the task's fixed executable/arguments, user SID, working directory, run level, trigger policy, protected install tree, and task DACL. The request path revalidates and invokes `IRegisteredTask.Run` on the same COM task object. The updater registration path remains disabled. One elevated read-only `Check` returned exit code 0; a subsequent non-elevated `Check` reported that the fixed `AeroTune-SignedUpdater` task is not registered. Both checks queried only that exact task and made no changes; the full Task Scheduler was not enumerated, and no task was registered or run. The host install-path/ACL check completed, but the runtime task definition/DACL has not been validated against an actual registered task; keep attestation off until a disposable-VM integration test does so. Tauri's Windows install path exits the updater process immediately after launching NSIS, so a rollback supervisor must live outside the executable/tree being replaced, wait for the installer result, and verify or restore the prior signed release. The current task target (`AeroTune.exe`) is not a safe long-lived supervisor while NSIS replaces that tree; before enabling, provision a separate fixed updater host outside the app root (or a trusted system-hosted supervisor), with staging, journal, and recovery artifacts in a ProgramData location protected by explicit DACL/reparse checks. A global named mutex now serializes current-build app launches and the helper across sessions for the same user; its Windows unit test covers thread-level exclusion, but cross-process/session behavior, cross-user fail-closed behavior, and compatibility with older builds still need disposable-VM validation. A same-user process can pre-create/hold the mutex and cause denial of service; that fails closed and cannot authorize an install ([Windows namespace guidance](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces), [CreateMutexW security remarks](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw)). Helper diagnostics currently use best-effort stderr and still need protected persistent logging. Preflight and updater contract tests run in the dedicated `npm run build:updater-release` command, and the `npm run tauri` package alias now guards build commands. Direct `npx tauri`/external CLI invocations can still bypass this check; no signing/publishing workflow is configured, so only artifacts produced by the guarded release command may eventually be published.

The global mutex rejects `WAIT_ABANDONED` and intentionally does not release it normally, so queued waiters also inherit the fail-closed condition. This baton only covers currently waiting processes; it does not persist recovery state across later launches. Before any installer launch, a protected transaction journal and recovery supervisor must distinguish an ordinary app crash from a helper crash mid-install and prevent startup until recovery/rollback completes. A strict schema/state machine, a read-only Windows startup gate, and a private atomic journal writer now exist in [update_recovery.rs](src-tauri/src/update_recovery.rs). The gate is conditional on `RECOVERY_STORE_REQUIRED` for whether the store must exist: while flags are hard-off, a missing ProgramData updater store is tolerated, and the known ProgramData volume/root is still opened without following reparse points. A same-name root is treated as a store only if its owner/DACL match the protected policy; untrusted user-created roots are ignored read-only and never removed, avoiding a ProgramData startup-denial vector. A trusted protected store is inspected and any partial or non-empty `State` directory blocks startup. Strict owner/DACL validation is mandatory when recovery is enabled; an absent or untrusted optional store does not block ordinary startup. If readiness is enabled, the store becomes mandatory; it requires a drive-root `ProgramData` on a fixed local volume with the checked-in trusted ACL, then requires pre-provisioned `%ProgramData%\AeroTuneUpdater\State` directories with SYSTEM/Administrators ownership and the exact protected DACL (SYSTEM/Administrators full control; Authenticated Users read/execute). Missing directories, ACL/path/reparse mismatches, or any state entry block startup. The writer is not integrated and does not provision directories or recover transactions, so no update transaction can yet be safely performed.

The bounded downloader now returns a private-field `VerifiedUpdateArtifact` only after Tauri verifies the exact bytes/signature and the archive validator accepts them. It binds those bytes to the parsed target SemVer and SHA-256, and exposes a read-back check that rejects a length mismatch before hashing a future staged copy. The future file reader must still enforce the artifact byte cap. A private journal factory accepts verified update and rollback artifact values, derives both recorded hashes from those values, and requires the rollback artifact's version to match the installed version exactly. Neither the read-back check nor this type boundary is wired to filesystem staging or the journal writer; all update and recovery gates remain off.

The private writer API requires an `UpdateGateGuard` witness, refuses calls while `RECOVERY_STORE_REQUIRED` is false, is not callable from other modules yet, and only accepts an already-provisioned verified store. It creates `prepared` only in an empty directory; advances only the exact on-disk predecessor by one legal phase with immutable IDs, versions, and hashes; bounds JSON; uses a same-directory `CREATE_NEW` temp with a protected DACL including an OWNER RIGHTS `WRITE_DAC` deny (the [OWNER RIGHTS SID](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-identifiers) suppresses the owner's implicit `WRITE_DAC`); loops partial writes, flushes, and commits with `MoveFileExW` write-through (replace only for a successor). It reopens and verifies the file ID, DACL, content, and directory entries. After temp creation, failures never delete the temp or canonical record; unknown or leftover temp entries block and are never silently cleaned. The commit sequence has fake-I/O failure-injection coverage. Before creating any file, the Windows adapter now uses `AccessCheck` with the effective thread token (falling back to the process token only when no thread token exists) for `FILE_GENERIC_WRITE | FILE_READ_ATTRIBUTES`, matching the writer's open rights. A token without those rights is rejected without creating a temp or canonical entry, rather than committing and later failing final-handle verification. An in-memory `AccessCheck` test with the Administrators SID disabled confirms a non-SYSTEM current-user owner with Authenticated Users membership is denied `WRITE_DAC` while retaining read access (the test skips under LocalSystem or when Authenticated Users membership is absent or disabled). A disposable temp-directory test verifies the current token is refused before writes; no elevated success run, provisioned ProgramData fixture, actual installer, or crash/recovery run has been tested. The helper still requires an actually elevated fixed runner and never prompts or elevates itself. Its path-based enumeration/open sequence pins protected directory handles and rechecks directory identity, but is not a defense against a malicious local administrator swapping ancestors; the threat model must exclude local admins or a future version must use native handle-relative opens. A separate supervisor must own recovery and terminal cleanup.

## Recovery decision matrix (design; supervisor not implemented)

When `RECOVERY_STORE_REQUIRED` is enabled, the startup gate blocks on every journal entry, including terminal phases; in this build the hard-off flags keep the store optional: absence is tolerated, but a present store is inspected read-only and unknown state still blocks startup. A separate, protected supervisor outside the replaceable app tree must resolve the journal before AeroTune can start. It also needs a distinct recovery-mode path for an abandoned `Global\AeroTune.SignedUpdateGate`: the ordinary app continues to reject `WAIT_ABANDONED`; the supervisor may use the acquired mutex only as an exclusion signal, then must validate the journal/artifacts before acting and retain exclusion through terminal verification/cleanup. `WAIT_ABANDONED` is never normal success, and uncertainty leaves startup blocked. The following rules are normative; uncertainty always means preserve evidence and keep startup blocked.

| Journal phase | Required recovery decision |
| --- | --- |
| `prepared` | The protocol has not yet recorded install intent. Verify the installed tree still matches the authenticated `from_version`; revalidate the signed target and rollback artifacts, hashes, architecture, and protected staging. Resume only by recording `install_intent` first; otherwise remain blocked for operator repair. Never silently delete the journal. |
| `install_intent` | Installer launch/completion may be ambiguous. The supervisor must own and wait for the installer process tree to quiesce before inspecting the installed manifest/version. Advance to `installer_observed` only when the expected signed target is fully present. Attempt rollback only after proving no installer process can still mutate Program Files; otherwise remain blocked. Never infer success from a missing process. |
| `installer_observed` | Verify the complete installed file manifest and target version against the signed release. Advance to `verifying` only on an exact match; otherwise record `rollback_required`. |
| `verifying` | Recheck signature-bound release metadata, version progression, and installed hashes. Advance to `committed` only when all checks pass; on any mismatch record `rollback_required`. |
| `rollback_required` | Verify the retained prior-release artifact's signature and signed-version binding with the pinned public key; the verifier must report exactly the journal's `from_version`. Independently match `rollback_artifact_sha256` and strict size/path limits. Journal strings or an unsigned feed version alone are not trusted. If unavailable or invalid, preserve evidence and block; otherwise record `rollback_intent` before restoring. |
| `rollback_intent` | Restore idempotently from protected staging. After a crash, do not assume restoration completed; revalidate every expected prior-version file/hash before recording `rollback_observed`. Ambiguity remains blocked. |
| `rollback_observed` | Independently verify the exact prior version and complete file manifest, then record `rolled_back`. |
| `committed` / `rolled_back` | Terminal does not mean startup-ready: verify the corresponding installed state, then use a separate, narrowly scoped supervisor cleanup operation (not the writer's `advance` API) that validates the terminal record, file identity/DACL, and recovery-mode mutex ownership before deleting only the canonical journal. Re-enumerate to prove the directory is empty. If cleanup errors or the journal reappears after a crash, keep startup blocked and retry recovery; never use delete-on-reboot. No such cleanup API exists yet. |
| Unknown phase, corrupt record, temp/unknown directory entry | Never start, overwrite, or silently clean. Preserve evidence and require the trusted recovery path or administrator repair. |

This matrix is design only: no supervisor, artifact restoration, terminal cleanup, or crash/restart integration exists yet. A normal older NSIS installer is not a rollback mechanism. Additional release-policy caveat: Tauri has a separate [`bundle.windows.allowDowngrades` setting](https://v2.tauri.app/reference/config/), whose default is `true` and is unrelated to `plugins.updater.allowDowngrades`. The base config now explicitly sets it to `false`; both release preflight and the Cargo build script reject overlays that enable or erase it. They also pin NSIS `installMode` to `perMachine`, reject the accepted `install-mode`/`installer-hooks` serde aliases, custom NSIS templates, hooks, and language source files (custom hooks execute elevated script), and require any NSIS overlay to repeat the protected mode explicitly. The base bundle and every signed-updater overlay must also target exactly `["nsis"]`; MSI, `all`, and omitted release targets are rejected. The updater release overlay is allowlisted to `$schema`, `bundle`, and `plugins`, with nested key allowlists that reject a Windows `signCommand`, NSIS `installDir`/hooks/template, custom updater headers, and any unreviewed install-setting override; it cannot replace the base app window or inject a build hook. The preflight accepts only regular, non-symlink, valid-UTF-8 JSON overlay files up to 64 KiB and checks file identity/metadata before and after reading. A direct, unwrapped Tauri CLI build using the default Cargo runner with an unsafe `--config` overlay was verified to fail in the build script before bundling. The pinned updater's `Update::download()` buffers the full response without a size cap. The currently gated path never calls it; before enabling any download path, implement bounded streaming with strict byte/time limits, preserve the HTTPS/DNS redirect policy across all hops, cap archive entry count and expanded size, and reject traversal/reparse points before staging. After streaming, call Tauri `Update::verify` on those exact bytes (including signed-version binding) and independently require strict SemVer progression before staging; do not use the default `Update::install` path, which stages under user temp instead of the protected transaction area.

## Required before enabling updates

1. Operate a public HTTPS release feed on a stable DNS hostname (IP-literal hosts are rejected) and define retention for the current and previous signed NSIS artifacts.
2. Generate a Tauri updater keypair outside the repo; protect and back up the private key. Put only the public key into a local release config. The preflight requires exactly one input: a non-placeholder `TAURI_SIGNING_PRIVATE_KEY` value (if path-like, it must be a non-empty regular non-symlink file outside the repository) or an existing non-empty regular non-symlink `TAURI_SIGNING_PRIVATE_KEY_PATH` file outside the repository ([Tauri environment variables](https://v2.tauri.app/reference/environment-variables/)). The preflight checks that file-based key inputs are non-empty, regular, non-symlink files outside the repository; it does not inspect Windows ACLs or prove a CI secret-store policy, which are separately hard-gated as not ready until external release review. Do not paste the private key into chat or commit it.
3. Review and measure the vendored feed-manifest patch before enabling checks: it caps responses at 256 KiB, rejects oversized `Content-Length`, counts streamed bytes when length is absent, and rejects truncation/invalid JSON. The bound is a prototype, not release-approved; retain the feed hard-off gate until the cap is checked against real metadata and the patch is reviewed.
4. The selected policy preserves Windows system-proxy use. Keep the updater's `system-proxy` feature enabled; for direct connections, implement connection-time DNS destination validation/pinning, and for proxied connections treat the approved proxy as the egress boundary with a reviewed proxy/host allowlist. The proxy resolves the origin hostname, so local DNS pinning cannot attest that destination; retain HTTPS hostname checks and signed-artifact verification. Reject `noProxy` and explicit proxy overrides unless separately reviewed; the bounded downloader now refuses either override. Test redirects, system-proxy use, and proxy-failure behavior on a disposable Windows VM. `UPDATE_DNS_DESTINATION_POLICY_READY` and `UPDATE_PROXY_POLICY_READY` remain false until review and VM validation.
5. Measure candidate signed NSIS payloads and choose reviewed numeric compressed/expanded byte caps; enforce `Content-Length` as an early check and an authoritative streaming byte counter even when length is absent. The prototype uses a 64 MiB compressed transport cap and a 128 MiB actual-expanded cap; after signature verification it accepts only a ZIP with one root-level unencrypted `AeroTune_...-setup.exe` NSIS installer, rejects MSI, non-setup executables, wrong-product names, links, and traversal, and drains the member to EOF/CRC under that cap. Neither limit is release-approved until measured against the signed target package; direct EXE/MSI updater payloads are currently rejected. Add a strict time cap, independently require strict SemVer progression, and write only to protected staging. Do not call the unbounded `Update::download` or user-temp `Update::install` paths.
6. Complete and test the dedicated protected updater runner and its fixed, run-only task, external ProgramData supervisor/journal, installer-result verification, and rollback. Provisioning requires one legitimate administrator approval, which cannot be silently or programmatically approved.
7. Test signed upgrades, interruption at every journal phase, and rollback on a disposable Windows VM. Keep the ordinary per-machine installer as recovery path.
8. Enable `bundle.createUpdaterArtifacts`, `requireSignedVersion`, the HTTPS endpoint, and release preflight only after steps 1–7 pass review and acceptance.

**Principal limitation:** the current task scaffold binds its interactive principal and run-only task ACL to the account that registers it while elevated. It therefore supports only that same logged-on administrator identity; a standard user whose UAC prompt uses a different administrator account cannot trigger this task. The task script's default path comes from the system Program Files known folder and rejects overrides other than the exact `Program Files\AeroTune\AeroTune.exe` target. Until a separately reviewed multi-user/SYSTEM-runner design is implemented, those users must use the ordinary per-machine installer and its normal UAC consent. Do not broaden task run rights or silently assume another administrator context.

The checked-in `tauri.conf.json` intentionally remains updater-disabled. `src-tauri/tauri.updater.example.json` is a deliberately unusable template (placeholder key and reserved `.invalid` feed); it must not be passed to a release build. `scripts/check-updater-release-ready.mjs` validates a local overlay supplied through `AEROTUNE_UPDATER_CONFIG` without printing signing secrets; by default it confirms that update delivery remains disabled. The strict `--required` mode refuses a signed-updater release when configuration is absent, and current per-machine builds remain blocked until rollback and privileged Windows validation are complete.

**Artifact URL validation scope:** the Node release preflight validates configured feed endpoints (HTTPS, multi-label DNS, default port, no credentials/query/fragment/trailing dot, and no reserved/local names; rejection messages do not echo the full URL); the future artifact URL is only known after a feed response. The Rust runtime validates feed and artifact URLs independently before use: HTTPS/default port, multi-label DNS syntax, no credentials/IP literals/trailing dots/reserved or internal suffixes; feed URLs reject queries and fragments, while artifact URLs may retain signed CDN query parameters but reject fragments. The updater client's custom redirect policy allows at most three hops, and each prior/next URL must pass the same HTTPS/DNS-host checks. The bounded request builder rejects any unreviewed custom artifact headers (none are configured), applies the same redirect/30-second timeout policy, and rejects explicit `noProxy` or custom-proxy overrides so automatic Windows system-proxy routing stays active; VM verification is still required. The Cargo dependency is pinned exactly to 2.14.0 and patched locally while this version-sensitive `configure_client` hook is relied upon; all updater requests have a 30-second timeout. Unit tests cover the URL decision function and run a local HTTP redirect through the configured client; actual HTTPS feed/CDN redirect behavior still requires disposable-VM integration validation. **These checks validate hostname syntax only, not DNS answers:** a public-looking name can resolve to loopback/private/link-local/ULA addresses or rebind. A separate hard-off destination-policy gate requires direct-route connection-time address validation/pinning or a reviewed system-proxy egress/host allowlist and DNS-rebinding tests before enabling. The pipeline, DNS destination, system-proxy, bounded-download, and task-attestation gates are hard-off, so no artifact is currently downloaded.

## Disposable Windows VM acceptance matrix (not yet executed)

| Scenario | Required result before any release gate can be enabled |
| --- | --- |
| Signed, strictly higher SemVer NSIS release | Verify the pinned signature, architecture, staged hashes, protected paths, and complete installed manifest; commit only after the supervisor independently verifies the installed target. |
| Missing/invalid signature or wrong public key | Refuse before installer launch; leave Program Files and the transaction journal unchanged except for a fail-closed diagnostic. |
| Equal/older version or build-metadata-only difference | Reject as no SemVer precedence increase; never stage or launch NSIS. |
| Non-HTTPS, literal/alternate-form IP host, or HTTPS-to-HTTP redirect | Reject the feed/artifact path before installer launch; audit every redirect hop and do not rely on the initial URL alone. |
| Direct-route DNS answer is loopback/private/link-local/ULA, or rebinds between checks | Reject before connecting; prove the validated answer is the address actually used by the socket on every redirect hop. |
| Windows system proxy is configured, bypassed, or unavailable | Preserve system-proxy routing; reject `noProxy`/explicit proxy overrides, prove no silent direct fallback, and have the approved proxy egress policy reject private destinations/rebinding because the proxy resolves origin DNS. |
| When recovery is required or a protected store is present: missing/foreign ProgramData ACL, reparse point, unknown journal/temp entry, or tampered staging | Keep the startup/update gate blocked and preserve evidence; never repair/delete unknown state automatically. |
| Forced process termination at each journal phase, including installer and rollback intent | On restart, the external supervisor must block normal startup until it proves the installed target or restores and verifies the prior signed manifest. Ambiguous process state remains blocked. |
| Invalid rollback signature/hash or missing previous artifact | Remain blocked and preserve evidence; a valid previous signed artifact must restore idempotently and pass full manifest verification. |
| Unregistered/foreign task, altered DACL/action/path, or unexpected trigger | `Verify` must fail and `Run` must not occur; registration stays hard-off in this build. Any later VM registration test requires a separately reviewed build and explicit administrator consent. |
| Concurrent launches/update requests and unsupported principal | Prove no overlapping installer; verify the same-admin limitation is enforced and a standard user cannot broaden task rights. |

Retain the VM snapshot identifiers, signed feed/artifact hashes, before/after installed manifests, task definition/DACL evidence, journal transitions, process exit codes, and recovery logs. This checklist is a test plan, not test evidence; none of these end-to-end scenarios has passed, so both readiness gates must remain false.
