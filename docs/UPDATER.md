# Windows updates: Tauri + GitHub Releases

## Current status

The ordinary AeroTune app has a narrow Rust IPC façade for the standard Tauri updater. The base Tauri config remains disabled; the owner authorized an early-access GitHub release sequence (v1.5.10 bootstrap, then v1.5.11 in-app update) and the release builds embed the configured production public key. The public v1.5.10 release was installed as the bootstrap. On 2026-11-01, that installed app found public v1.5.11 through Settings, launched the updater install, and exited; the Program Files executable and uninstall registry then reported 1.5.11, and a manual relaunch showed v1.5.11. The release archive and manifest signature were independently verified. Current updater logs do not emit individual redirect hops; success proves the allowlisted request path worked, but does not capture its exact chain. The UAC interaction itself was not captured; cancellation after setup starts, concurrent launch, interrupted/file-in-use recovery, and repair remain untested and are not represented as passed.

The base app config stays updater-disabled (no public key, no endpoint, and `createUpdaterArtifacts: false`). `src-tauri/tauri.updater.example.json` is a template; the release workflow fills its public key from the GitHub repository variable `AEROTUNE_UPDATE_PUBLIC_KEY` into a temporary overlay. Only the ordinary Tauri plugin is registered for Rust use; no `updater:` JavaScript capability is granted.

## Update flow

1. Settings offers a manual **Check for updates** action. Rust creates the Tauri updater through `UpdaterExt`, with a fixed feed at `https://github.com/shengqiangdd/AeroTune/releases/latest/download/latest.json`.
2. Feed requests use HTTPS/TLS validation, a 30-second timeout, the patched 256 KiB manifest response cap, automatic system-proxy behavior, and a maximum of three redirects limited to GitHub release paths and GitHub's release-asset hosts. Artifact URLs announced by the feed must be versioned `github.com/shengqiangdd/AeroTune/releases/download/...*.nsis.zip` URLs; the downloader does not accept arbitrary hosts or a direct CDN URL from the manifest.
3. The install button asks for explicit confirmation, then Rust rechecks the feed and verifies that the version still equals the displayed version. A bounded download (64 MiB compressed) is checked with Tauri's Minisign signature and signed-version binding, then the ZIP is restricted to one root-level AeroTune NSIS setup executable within the 128 MiB expanded cap. Tauri `Update::install(bytes)` verifies the signature again before launching its standard installer path.
4. NSIS uses `passive` mode and the normal installer is configured `perMachine`. `passive` is not an elevation setting: the per-machine installer must request Windows UAC. Tauri exits AeroTune after launching NSIS and does not automatically restart it; the user relaunches the app after installation. The process mutex therefore does not serialize any later launch against the still-running installer, so local acceptance must explicitly test launching AeroTune during an update; if this can interfere, keep the updater disabled. The Settings confirmation is a user-experience prompt, not a security boundary; the custom IPC command remains callable by the bundled webview.

The updater URL allowlist relies on HTTPS certificate validation and the fixed GitHub host/redirect policy; it does not pin DNS answers. No credentials or custom proxy overrides are sent. The pre-update proxy snapshot showed WinHTTP direct access, WinINet proxy/auto-config disabled (a stored proxy-server value was inactive), and no standard proxy environment variables. The v1.5.11 in-app update succeeded under this observed configuration. The current Rust downloader does not log individual redirect hops, so acceptance proves that the allowlisted GitHub path worked, not the exact redirect trace. DNS answers are not pinned.

## Signature and installation limitations

GitHub's `latest.json` is unsigned metadata. Tauri verifies the downloaded artifact with the embedded public Minisign key and, with `requireSignedVersion: true`, binds the announced version to the signed artifact. Downgrades remain disabled. The private key is only for Tauri updater signatures; it is **not Authenticode** and does not identify AeroTune as the publisher in UAC or establish SmartScreen reputation. Without a separate Authenticode certificate, Windows may show an Unknown publisher prompt.

The standard Tauri updater stages the signed NSIS payload in the current user's temporary directory and does not provide AeroTune's former protected transaction journal or crash-safe rollback. This design intentionally does not restore the custom scheduled task, ProgramData store, or rollback supervisor. Interrupted, canceled, file-in-use, and concurrent-install behavior still require testing with a recorded repair plan. The owner explicitly accepted early-access releases before these cases are closed; they remain blockers for a general-availability claim.

## Keys and release procedure

1. A production Tauri updater Minisign keypair has been generated outside the repository. Its public key is the repository variable `AEROTUNE_UPDATE_PUBLIC_KEY`; its private key is in the `TAURI_SIGNING_PRIVATE_KEY` secret for the GitHub Environment `aerotune-release`, which requires owner review and restricts deployments to `main`. Keep the private key out of source and create an offline recovery backup before general availability.
2. The owner authorized the early-access sequence even though the GitHub redirect/system-proxy path and cancellation, concurrent-launch, interruption, and repair cases are not all tested. The release gates in `src-tauri/src/updater.rs` reflect that decision; see [UPDATER_RELEASE_BLOCKERS.md](UPDATER_RELEASE_BLOCKERS.md) for residual risk. Do not claim the unrun cases passed.
3. Synchronize `Cargo.toml`, `package.json`, and `tauri.conf.json` versions, update the changelog, create and push a `v<version>` tag pointing at the reviewed `main` commit, and keep the checkout clean.
4. Dispatch `.github/workflows/release-windows.yml` from `main` with that existing tag. The job uses read-only permissions for validation and scopes `contents:write` to the release job. It sets `createUpdaterArtifacts` to `v1Compatible` because AeroTune's bounded installer validator consumes the signed NSIS `.nsis.zip`; Tauri's default v2 mode signs the raw `.exe` instead. This compatibility mode is deprecated for Tauri 3, so migrate the bounded validator to direct-EXE payloads before a Tauri major upgrade. The job builds the signed installer and `.nsis.zip`/`.sig`, constructs `latest.json`, and refuses to replace an existing GitHub Release.

The manifest generator publishes the Tauri target `windows-x86_64-nsis`, the versioned GitHub download URL, and the base64-encoded contents of the `.sig` file. The standalone installer is included for first-time/manual installs; the updater archive and signature are required for in-app updates. The workflow does not sign PE files with Authenticode.

## Local Windows acceptance

Completed 2026-10-31: the actual AeroTune app advanced the installed Program Files version from 1.5.10-local.3 to .4 through a temporary Settings-page entry calling the existing Rust updater IPC and bounded downloader against a loopback-only feed. The manifest and signed archive returned HTTP 200; signature/version and ZIP/PE checks passed; user-approved UAC launched per-machine NSIS; registry, executable, startup log, and manual relaunch showed .4. The run exposed the x86 NSIS bootstrapper for an x64 bundle; the validator now permits that PE32 stub while retaining the signed target-specific archive filename check. The local disposable key and overlay were removed and the loopback server stopped. This proves the actual app IPC/downloader/install path, but not the production GitHub host/redirect/proxy route. The test installer is Authenticode-unsigned.

Production acceptance, 2026-11-01: workflow run `41264899765` published [v1.5.11](https://github.com/shengqiangdd/AeroTune/releases/tag/v1.5.11) from tag commit `f86962b2336752fe5904b5461b372551d3d5bd17`. The installed v1.5.10 app's Settings updater found v1.5.11; after installation the app had exited, and manually launching `C:\Program Files\AeroTune\aerotune.exe` showed v1.5.11. The Program Files executable and HKLM uninstall entry both report 1.5.11. WinHTTP direct/WinINet proxy-disabled was the observed configuration; the update succeeded under it. The UAC dialog details were not captured, and current app logs do not expose individual redirect hops. Exact asset hashes and signature verification are recorded in [UPDATER_RELEASE_BLOCKERS.md](UPDATER_RELEASE_BLOCKERS.md).

Still untested and not claimed as passed:

- Canceling the app confirmation or UAC; offline and configured system-proxy failures.
- Interrupted download/install, file-in-use, duplicate update requests, launching AeroTune while NSIS remains active, and repair by rerunning the installer.
- Elevated and standard-user invocation across supported Windows builds.

The release gates are enabled for owner-authorized early access. General availability remains blocked until the residual Windows cases and recovery plan are tested and reviewed.
