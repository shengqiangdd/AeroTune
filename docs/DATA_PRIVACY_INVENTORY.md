# AeroTune technical data and privacy inventory

> This is a source-based engineering inventory, not a legal privacy notice. It describes the current implementation and needs product/legal review before a public release. It is not a packet capture or an audit of every transitive dependency.

## Runtime data and network activity

The production Tauri WebView policy is now default-deny: it permits same-origin bundled scripts, styles, the local app icon, and the two documented Tauri IPC sources; remote resource origins, frames, workers, media, and fonts are denied. The separate development policy adds only the Vite HMR websocket and dev-server CSS injection allowance. This follows [Tauri's CSP guidance](https://v2.tauri.app/security/csp/) and constrains WebView resource loading, not native Rust networking such as the explicitly invoked ICMP probe.

- The native sampler collects local CPU, memory/pagefile, disk, network-counter, GPU, battery, uptime, and process-count data for the dashboard and diagnostics. Process management and the diagnostic engine also temporarily hold process names, PIDs, metrics, and executable paths in memory; those details are not part of the diagnostic export schema. For identity-bound resume, the process list also holds an opaque FILETIME creation token in memory only; its derived UTC timestamp is shown in the process table, row tooltip, and resume confirmation. Neither value is persisted or included in exports.
- Startup inventory, service inventory (including service names and executable paths), logon-task inventory, adapter/DNS settings, Windows reliability events, and user-selected file scans are queried locally when their features are used. Service rows stay in memory unless the user explicitly exports a CSV; startup-type changes are recorded in the local change journal. File and duplicate scans may process user-selected paths and local file contents/hashes; they do not imply an upload.
- The network quality feature sends ICMP probes to the default gateway and the configured public probe addresses (`223.5.5.5` and `119.29.29.29`). It runs after a user probe or explicit observation start; the remote targets can observe the client's network address. The stored history contains timing/quality results, not SSIDs or destination addresses.
- A source scan found no frontend `fetch`/XHR/WebSocket/beacon analytics call. The base config remains updater-disabled; owner-authorized early-access release builds use the configured production key and make requests only when the user manually checks the fixed GitHub Releases feed. On 2026-11-01 the app updater successfully fetched and installed v1.5.11 under the observed WinHTTP-direct/WinINet-proxy-disabled configuration; GitHub may observe the client's network address and request metadata. App logs do not expose individual redirect hops, and no packet capture was performed. The optional WinGet software-update observation runs only after an explicit user confirmation, uses the App Installer package (not PATH), and invokes a fixed `list --upgrade-available --disable-interactivity` query. It may contact configured sources and update their local cache; WinGet may send source queries or package-identifying data according to the configured source behavior. It never accepts source agreements or installs/upgrades packages. Raw output is held only in the Settings view's memory and is not added to AeroTune logs or otherwise uploaded by AeroTune. This does not substitute for packet-capture or dependency-level verification.

| WebView `localStorage`: process history | Executable basename, CPU and memory summaries; no PID/path/command line | Default off; user opt-in; at most 20 names per sample, 5-minute minimum interval, 7 days. Executable names can still reveal app usage. |

The experiment-consistency analysis is stateless: the frontend sends these local summaries to a pure Rust function on read and nothing is persisted backend-side. |
| `%APPDATA%\AeroTune\auto_settings.json` | Automation preferences, custom game/protected-app names, rules, power-plan identifiers, mode-duration summaries; also the autopilot master flag, its auto-dispose sub-flag, and the pre-enable switch snapshot (seven booleans) | Persists until changed/deleted; no separate encryption layer. |

| `%APPDATA%\AeroTune\scene-shadow.json` | Per-executable-name counts of confirmed fullscreen sessions (total, per-local-day counts, last-seen timestamp) for the scene-learning suggestion list | Observation only; feeds user-approved game-list suggestions. Entries capped at 64 (oldest evicted); entries unused for 30 days are pruned; user "dismiss" removes one entry. No paths, PIDs, or window titles. |
| `%APPDATA%\AeroTune\residency-patterns.json` | Per-normalized-process-name aggregates observed only while AeroTune runs (30-minute samples: summed/max memory, low-CPU sample ratio, per-day counts, updater-name heuristic flag) | Observation only; feeds read-only residency suggestions. Entries capped at 128 (oldest evicted); 30-day staleness pruning; user "dismiss" removes one entry. Never includes protected/system processes or AeroTune itself; no paths or PIDs. |
| `%APPDATA%\AeroTune\disk-health-history.json` | Per-physical-disk SMART snapshots recorded at most hourly when the user opens the disk-health view (timestamp, health status, temperature, wear %, power-on hours, uncorrected read/write error counts) | Read-only observation; feeds trend hints (new errors / wear movement) in the cleaner page. Per-disk cap of 120 samples; disks unseen for 30 days pruned; user "dismiss" clears one disk. Collected only while AeroTune runs; not a life-expectancy forecast. |
| `%APPDATA%\AeroTune\brightness.snapshot` | Original and automatic-dim target brightness percentages; no path, process, or device identifier | Written atomically before an automatic brightness change. After a successful dim, adaptive recovery and all startup/exit recovery write the original only if live brightness still matches the saved dim target. If it already equals the original, or differs from both saved values (which may indicate an external change), the stale record is cleared without changing brightness. Unreadable/failed recovery retains the record for retry when possible. Not separately encrypted or included in configuration export. |
| `%APPDATA%\AeroTune\changes.json` | Change descriptions and undo snapshots (which can contain registry bytes, DNS addresses, plan identifiers, or settings) | No automatic eviction currently documented. Manual journal CSV/JSON omits undo snapshot values. |

| `%APPDATA%\AeroTune\plans_backup` | User-created power-plan backups | Kept until removed. |
| `%APPDATA%\AeroTune\logs` | Daily application logs; some operational records include process names/PIDs, paths, selected configuration paths, and command error output | Current logger rotates daily and now prunes only dated AeroTune log files older than 14 days at app startup. No in-app log-clear control. Review logs before sharing. |

The application data helper resolves the current token's Roaming AppData folder with Windows `SHGetKnownFolderPath` rather than trusting an inherited `APPDATA` value, then uses its `AeroTune` child directory. If resolution fails, `app_dir()` fails closed by panicking; it does not fall back to a relative path. Windows ACLs/profile protection apply, but AeroTune does not add an encryption layer to these files. The Settings page now exposes a concise summary and a detailed, source-based local-data/retention disclosure; this engineering inventory is not a legal privacy notice.

## Renderer file-system permissions

The main WebView capability has no filesystem-plugin permissions or dialog-open permission, and the Rust filesystem plugin is not registered for it. All seven frontend exports send bounded text plus a validated AeroTune filename to a Rust command; the command opens its own native Save dialog, receives the chosen path directly, and writes atomically. The renderer cannot supply an arbitrary target path or call filesystem/dialog-plugin APIs. Duplicate scanning opens the folder picker in Rust and returns only a short-lived random handle; the selected path stays in a bounded backend registry for scans/rescans. Disk scan commands accept named presets that Rust resolves to the user profile or Windows system drive. This avoids tying generic filesystem authority to renderer dialog/drop path scopes described in [Tauri's filesystem security model](https://v2.tauri.app/plugin/file-system/). Configuration import uses a pathless Rust command that opens the native JSON picker, keeps the selection in Rust, performs a bounded local-file read and validation, then applies the settings. The Rust config-export command performs its own local copy; these operations remain separate trust boundaries.

## Native command path boundary

The UI's picker/confirmation is not itself backend authorization. [`disk_analyzer.rs`](../src-tauri/src/disk_analyzer.rs) now resolves disk scans from a closed user-profile/system-drive preset enum and duplicate scans from a Rust-owned native folder selection represented by a 30-minute, bounded random handle; no scan command accepts a renderer-provided root path. Duplicate handles are revalidated on use and may be reused for post-delete rescans. `recycle_delete` requires a separate short-lived server-held scan grant; disk scope is limited to returned large files and duplicate scope to returned verified members. Backend checks canonical regular-file paths and the scan's size/mtime snapshot, claims each path before PowerShell, bounds/ages grants, and enforces keeping one visible copy per duplicate group across batches. A failed Shell batch burns its claims and the UI discards the result and rescans. These checks constrain scope, not user intent: a compromised renderer can still request the allowed disk presets or trigger the native folder picker, so assess trusted native confirmation before GA. `open_path` rejects UNC/device/ADS and relative inputs before filesystem probes, rejects network drives/reparse-point components, and canonicalizes existing local file/directory targets before invoking Explorer; its callers surface validation failures. Config import opens a Rust-owned native JSON dialog, keeps the selected path out of the renderer, reads at most 1 MiB from a local regular file, validates the settings, and applies them in one command. Startup file moves in [`startup.rs`](../src-tauri/src/startup.rs) require a canonical direct child, a regular supported file, and trusted source/destination directories; common Startup changes require an elevated token. `set_task_state` also repeats the enumerator's `\\Microsoft*` exclusion in Rust and validates task folder/name components before launching `schtasks`. `remove_residual` remains admin-gated and limited to a fixed allowlist; Rust now requires a native warning/OK-Cancel confirmation and checks the full descendant tree without following reparse points before recursive ownership/ACL changes, failing closed on inspection errors, the entry cap, or its elapsed-time budget between filesystem entries (individual OS calls are not cancellable); failed `takeown`/`icacls` commands abort before `rd`, and the root is rechecked immediately before deletion. Concurrent filesystem races and native-prompt sufficiency against compromised-renderer intent still require Windows VM review. Continue reviewing local filesystem race assumptions; the shared child-process runner resolves PowerShell and common Windows utilities from the OS-reported system directory, verifies ordinary executable targets, and fails closed instead of searching PATH; plugin capabilities do not authorize application-defined commands. See the command-path item in [RELEASE_READINESS.md](RELEASE_READINESS.md).

Residual-item discovery now uses the bounded no-follow walker with a single-flight gate; roots that cannot be fully inspected remain visible with unknown size and deletion disabled. The delete command independently repeats the full-tree preflight and refuses files whose handle-reported hard-link count exceeds one before recursive ownership/ACL changes. Concurrent filesystem mutation remains a Windows VM review item.

## Explicit exports

- **Diagnostic report:** generated locally after the user asks for a preview. The final JSON is allowlisted; host name, CPU/GPU model and core count, plus detailed metrics/timestamps, are omitted by default. Separate checkboxes opt those groups in. The final JSON is available for inspection before the user clicks save and chooses a path. Unknown future fields are discarded by the exporter. The schema currently excludes process names/paths and Wi-Fi/network credentials.
- **Configuration export:** user-triggered local copy of automation settings. Inspect it before sharing; custom app names and power-plan identifiers may be present.
- Neither export is automatically transmitted by AeroTune.

## Source integrity caveat

The workspace lacked VCS metadata or a backup while [`lib.rs`](../src-tauri/src/lib.rs) was being changed. Its prior full text could not be recovered; the current app crate was reconstructed from captured fragments and command contracts, then compiled/tested and checked against all 116 frontend IPC commands. It is not a byte-for-byte restoration of an authoritative revision. Obtain/compare with an authoritative source revision before merging or releasing.
